Локальное приложение для закупщика: загрузить договоры и связанные документы,
увидеть действующую сумму, срок поставки и ставку неустойки, открыть основание
в исходном тексте. У каждого значения есть файл и точная цитата. Если сведений
недостаточно или они противоречат друг другу, приложение показывает это в результате.

## Запуск

Понадобятся Python 3.13 и [uv](https://docs.astral.sh/uv/getting-started/installation/).
Если uv ещё не установлен, его можно поставить командой `python -m pip install uv`.

Распакуйте архив, откройте терминал в папке `semantic-textnavigator` и выполните:

```bash
uv sync --locked
uv run python -m app
```

Откройте [http://127.0.0.1:8000](http://127.0.0.1:8000).
Остановка сервера — `Ctrl+C`. При занятом порте:

```bash
uv run uvicorn app.app_factory:create_app --factory --host 127.0.0.1 --port 8001
```

Для установки зависимостей нужен интернет. После установки приложение работает
локально, без аккаунтов, API-ключей и обращений к модели. Интерфейс отдаёт тот же
Python-сервер; Node.js и сборка фронтенда для запуска не нужны. Версии зависимостей
зафиксированы в `uv.lock`.

## Как проверить

1. Нажмите **«Загрузить учебный комплект»**. Можно также выбрать все шесть файлов
   из `examples/documents` через загрузку. Дата проверки по условию — **10.03.2026**.
2. Воспользуйтесь кнопками **«Контрольные вопросы» (1–4)** над таблицей — они
   в один клик применяют нужные фильтры, выбирают договор и открывают цитату с основанием.
3. Либо нажмите на сумму, срок или неустойку в любой строке таблицы вручную.
   Откроются основания, связанные документы и полный исходный текст с выделенным абзацем.
4. Посмотрите предложения: письмо и неподписанный проект показаны отдельно от
   действующих условий. У изменённого значения виден документ, который его заменил.
5. Измените сумму, срок или неустойку в копии TXT, загрузите её заново. Добавьте
   новый договор того же общего формата. Анализ выполняется по содержимому каждого
   загруженного комплекта. Имена и порядок файлов не определяют приоритет.

Контрольные результаты исходного комплекта на 10.03.2026:

| Вопрос | Результат и основание |
| --- | --- |
| Какой срок действует по STN-101? | **30.04.2026**. Подписанное допсоглашение № 1 вступило в силу 01.03.2026. Проект со сроком 10.05.2026 остаётся предложением. |
| Какова сумма STN-102? | **840 000 ₽**. Аванс 252 000 ₽ входит в общую сумму. |
| Какова сумма STN-103? | **Нет данных**. Сумма вынесена в отсутствующее приложение № 1. Бюджетный лимит 600 000 ₽ не принимается за стоимость договора. |
| Какие поставки раньше 01.04.2026 и есть ли несогласованный перенос? | **STN-102: 20.03.2026**. Поставщик предлагает 27.03.2026, но подписанного соглашения об изменении нет. |

Дополнительно извлекается ставка неустойки:
- **STN-101**: **0,1% в день** (сохранена допсоглашением № 1 без изменений);
- **STN-102**: **0,05% в день**;
- **STN-103**: **Нет данных** (в тексте договора прямо зафиксировано, что ставка не установлена).

У STN-101 также действует сумма **1 380 000 ₽** из подписанного допсоглашения.
Предложенные **1 450 000 ₽** показаны в проекте отдельно.

При новой загрузке комплект заменяется целиком. Чтобы учесть изменение, загрузите
базовый договор вместе с относящимися к нему документами. Смена даты требует
повторного анализа; подпись результата показывает дату, на которую он рассчитан.

## Проверки

```bash
uv run pytest
uv run ruff check .
uv run ruff format --check .
uv run mypy
```

Дополнительно можно посмотреть покрытие:

```bash
uv run pytest --cov=app --cov-report=term-missing
```

Тесты проверяют исходный комплект, изменённые поля и новый договор, влияние даты
проверки, подписи и даты вступления в силу, конфликтующие редакции, отсутствие
сведений, точность цитат и их координат. HTTP-проверки используют настоящий API
через тестовый клиент, включая ограничения загрузки и независимость запросов.

## Ограничения прототипа

- Вход: от 1 до 50 TXT-файлов в UTF-8, включая UTF-8 с BOM. До 1 МиБ на файл и
  10 МиБ на комплект. PDF, DOCX и сканы не поддерживаются.
- Поддержаны русские формулировки общего формата учебного комплекта: номер
  договора, явно указанный поставщик, итоговая сумма цифрами в рублях, календарный
  срок в формате `ДД.ММ.ГГГГ`, текстовый статус подписи и дата вступления в силу.
- Суммы прописью, расчёт НДС, относительные сроки, графики отдельных партий и
  произвольная юридическая формулировка условий не разбираются. Непонятное
  распознанное условие требует проверки; неизвестный текст можно открыть вручную.
- Статус подписи извлекается из текста. Электронная подпись и подлинность документа
  не проверяются. При одинаковых датах силы и разных условиях нужен человек.
- Результат относится только к загруженному комплекту. Приложение не знает о
  документах, которых в нём нет. Исходные TXT не редактируются и не сохраняются
  приложением; после обновления страницы комплект нужно загрузить снова.
- Сервер предназначен для локального запуска. Пользователи, права доступа,
  постоянное хранилище и промышленное размещение в прототип не входят.

## Продуктовая и техническая записка

### Пользователь и задача

Сделал прототип для специалиста по закупкам, который сверяет условия перед
дальнейшей работой с поставщиком. Ему нужны действующие условия на конкретную
дату и быстрый переход к документу. Поэтому основа интерфейса — таблица и
исходный текст рядом. Результат можно проверить до принятия решения.

### Пять вопросов клиенту

1. Какое действие следует за сверкой: подтверждение заказа, контроль поставки,
   согласование изменения или подготовка претензии?
2. Какие форматы, шаблоны и языки встречаются чаще всего; сколько документов
   проверяют за день и сколько времени занимает ручная сверка?
3. Где находится достоверный статус подписи и кто разрешает конфликт редакций,
   когда номера, стороны или даты не совпадают?
4. Какие условия, кроме суммы и срока, обязательны для первого рабочего запуска:
   частичные поставки, НДС, авансы, неустойка, спецификации?
5. Кто имеет доступ к договору, его приложениям и истории изменений; бывают ли
   документы, доступные только части сотрудников одной компании?

### Допущения

Использую правило из задания: условия меняет подписанное обеими сторонами
допсоглашение после наступления даты его силы. Дополнительно проверяю, что сама
подпись уже состоялась на дату анализа. Нужны явно указанные даты подписи и силы;
дату из заголовка вместо них не подставляю. Последовательные изменения применяются
по датам силы, а разные условия с одной такой датой требуют проверки. Название
файла и дата загрузки ничего не решают. Связь строится по номеру из текста;
противоречие указанных сторон требует проверки. Письма и проекты сохраняют
предложенные значения отдельно.

В этой версии сумма — итоговая стоимость в рублях, срок — явно названная
календарная дата поставки. Отсутствие значения и конфликт — разные состояния.
Неразрешённое изменение не даёт уверенного ответа по затронутому полю.

### Две метрики

**Качество ответа:** доля проверяемых полей, для которых одновременно верны
значение, действующая редакция и цитата на размеченном наборе документов.
Уверенный неправильный ответ считаю ошибкой, даже если число найдено в тексте.

**Время проверки:** медианное время решения четырёх рабочих вопросов с открытием
оснований по сравнению с ручным чтением тех же комплектов. Для первой оценки
нужны реальные закупщики и одинаковые задания; замеров на пользователях пока нет.

### Архитектура и решения

Браузер отправляет файлы и дату в FastAPI. HTTP-граница проверяет формат и размер,
анализатор выделяет абзацы и кандидатов, затем определяет применимость документов.
Ответ содержит условия, причины неопределённости и координаты цитат.

| Часть | Ответственность |
| --- | --- |
| `app/analysis` | Чистый разбор текста, связь документов, применение изменений, источники. |
| `app/web` | Загрузка файлов, ограничения, API и понятные ошибки. |
| `app/app_factory.py` | Сборка приложения и передача зависимостей. |
| `app/static` | Таблица, фильтры и просмотр исходного документа. |

1. **Правила вместо модели внутри приложения.** Для ограниченного формата это
   воспроизводимый результат и запуск без внешнего сервиса. Цена решения — узкая
   поддержка формулировок. Расширять её нужно на размеченных документах.
2. **Извлечение отделено от выбора действующей редакции.** Найденная дата сама
   по себе не становится условием договора. Это добавляет явные состояния,
   зато позволяет независимо проверять правила подписи, силы и конфликтов.
3. **Цитата хранит координаты исходного абзаца.** Проверка открывает тот текст,
   из которого получено поле. Передаём документ целиком ради простого локального
   просмотра; на большом корпусе понадобится загрузка отдельных страниц и версий.

Из своего ТАКТ перенёс Python 3.13, строгую типизацию, Pydantic на границе API,
неизменяемые внутренние DTO, фабрику приложения, явные зависимости, конкретные
исключения и проверки Ruff/mypy/pytest. Для этого сценария отдельная БД не нужна.

### Что изменится на 100 000 документов

Исходники будут храниться неизменяемыми версиями в файловом хранилище, метаданные,
абзацы, связи и извлечённые условия — в PostgreSQL. Загрузку и переобработку вынесу
в очередь, добавлю идемпотентность по хешу содержимого и версию правил извлечения.
Индексы по договору и датам позволят пересчитывать только затронутые связи.

Доступ к документам нужно проверять до поиска и расчёта ответа и повторно при
открытии цитаты. Чужой документ не должен попасть ни в результат, ни в подсказку,
ни в кэш. Ключ кэша учитывает набор версий, дату проверки и область доступа.
Исправления пользователя и изменения прав будут попадать в журнал аудита.

### Следующие улучшения

1. Собрать размеченные реальные договоры и измерить ошибки, особенно ложные
   подтверждения; расширить правила на частые формулировки.
2. Добавить разбор спорных случаев человеком: подтверждение связи, недостающего
   приложения и редакции с сохранением основания и истории исправлений.
3. Подключить нужные клиенту PDF/DOCX и OCR, сохранив переход к странице и цитате.
   После проверки сценария переходить к хранению, очередям и правам доступа.

## Как использовал ИИ

Фактическое время работы — около **30 минут** в одной сессии 13 ноября 2026 года,
включая изучение задания, реализацию, проверки и README. Оставшаяся проверка
указана в конце этого раздела.

Инструмент — ChatGPT с возможностями Codex: анализ задания и стандартов ТАКТ,
реализация, независимые тесты и проверка интерфейса. Модель внутри приложения
не используется.

Характерные рабочие запросы, сокращённо:

1. «Изучи актуальные AGENTS.md, настройки типов и реальные модули ТАКТ. Определи,
   какие правила нужно перенести в самостоятельное тестовое».
2. «Разбери загруженный текст без зашитых номеров, сумм и дат. Применяй только
   подписанные вступившие в силу соглашения. Для каждого поля верни точную цитату
   и координаты исходного абзаца».
3. «Независимо проверь новый договор, изменённые поля, порядок файлов,
   неподписанные и будущие изменения, конфликты и отсутствие данных».

**Ошибка ИИ и исправление.** В первом варианте код сравнивал поставщика, но
пропускал покупателя: подписанное допсоглашение с тем же номером и другой
компанией-покупателем ошибочно меняло условия. Независимый тест воспроизвёл
уверенный неправильный ответ. Добавил проверку обеих сторон и регрессию:
теперь затронутые поля получают статус «Нужна проверка», исходные основания
сохраняются. Проверил и несовпадение поставщика. Отдельными тестами закреплены
отрицание «не вступает в силу» и формулировка «остаётся без изменений» с буквой ё.

Проверка результата включает независимые примеры, точное сопоставление цитаты
с исходной строкой, HTTP-тесты API и запуск Uvicorn с настоящими HTTP-запросами.

### Что проверено и что осталось

Выполнены **55 Python-тестов**, Ruff check/format и mypy strict. Дополнительно
прошли **9 функциональных сценариев интерфейса** в jsdom: настоящие обработчики
страницы обращались к FastAPI TestClient, включая загрузку нового договора.
Проверены переход к точному абзацу, фильтры, повторный анализ, ошибки, очистка
и отображение HTML из документа обычным текстом. Эти дополнительные проверки
проводились в рабочей среде; для запуска самого приложения Node.js не требуется.

**Осталось проверить:** внешний вид и полный пользовательский проход в настоящем
браузере на рабочей машине. В среде разработки браузер и сервер оказались в
разных сетевых пространствах, а открытие локального HTML было запрещено политикой.
Функциональная проверка DOM не заменяет визуальную проверку. Скриншоты и
браузерный end-to-end прогон не заявляю как выполненные. Остальные направления
доработки перечислены выше в порядке приоритета.
